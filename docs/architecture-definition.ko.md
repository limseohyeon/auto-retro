# Auto Retro 아키텍처 정의서

## 시스템 목적

Auto Retro는 사용자의 개발 기록을 저장하고, 기록에서 요약을 생성하며, 일정 기간의 주간 회고와 발표 초안을 만드는 애플리케이션이다. 현재 저장소의 스키마와 패키지를 기준으로 사용자, 개발 기록, AI 생성, 주간 리포트, 발표 모듈을 핵심 영역으로 본다.

## 구조

하나의 Spring Boot 애플리케이션으로 배포하는 모듈러 모놀리스다.

```text
com.devlog.auto_retro
├── user
├── devrecord
├── aigeneration
├── weeklyreport
├── presentation
└── common
```

각 업무 모듈은 필요한 경우 다음 방향으로 구성한다.

```text
adapter/in → application → domain
application → port/out ← adapter/out
```

- `domain`과 `application`은 JPA, MVC, AI SDK 같은 외부 기술에 의존하지 않는다.
- 입력 어댑터는 요청 검증과 변환을 담당하고 애플리케이션 유스케이스를 호출한다.
- 출력 어댑터는 애플리케이션이 정의한 포트를 구현한다.
- 다른 모듈의 JPA Entity, Repository, 내부 구현을 직접 참조하지 않는다.
- 단순 CRUD에는 교체 가능성이나 경계가 없는 인터페이스를 만들지 않는다.

Spring Modulith가 명시적으로 선언된 업무 모듈과 의존 관계를 검증한다. 모듈을 추가하거나 공개 API를 변경할 때 `ModularStructureTests`를 함께 확인한다.

## 데이터와 일관성

PostgreSQL 스키마의 유일한 기준은 `src/main/resources/db/migration/`의 Flyway 마이그레이션이다. JPA 매핑은 이 스키마를 따라야 한다.

현재 주요 데이터 흐름은 다음과 같다.

```text
사용자
→ 개발 기록 + 태그
→ 기록별 AI 요약
→ 기간별 주간 리포트
→ 개발 기록 또는 주간 리포트 기반 발표 초안
```

중복 생성과 기간 충돌처럼 동시성에 민감한 비즈니스 규칙은 애플리케이션 조회만으로 보호하지 않고 유니크 키, 체크 제약조건 또는 적절한 잠금 전략을 함께 사용한다.

## 애플리케이션 경계

- REST와 Batch가 같은 기능을 제공하면 동일한 애플리케이션 유스케이스를 호출한다.
- 입력은 컨트롤러나 배치 입력 경계에서 검증한다.
- 비즈니스 오류는 `common.error`의 공통 예외와 오류 응답 형식을 사용한다.
- 인증, AI 모델, 외부 API, 저장소는 애플리케이션 포트 뒤에 둔다.
- 비밀값은 환경변수로 받고 프로필별 설정에는 비밀값을 넣지 않는다.

## 운영 및 LLM 관측성

서버 애플리케이션 관측성과 제품 LLM 관측성은 같은 실행 흐름을 추적하되 서로 다른 목적의 저장소에서 관리한다. 애플리케이션은 OpenTelemetry 표준으로 관측 데이터를 생성하고 공통 Collector를 통해 목적지별로 전달한다.

```text
브라우저 또는 Batch
→ Spring Boot 애플리케이션
→ OpenTelemetry Collector
   ├─ 로그·메트릭·전체 요청 Trace → Elastic
   └─ LLM 관련 Trace              → Langfuse
```

- Elastic은 HTTP 오류율과 지연시간, JVM, 데이터베이스, 외부 API, 애플리케이션 로그와 운영 알림을 담당한다.
- Langfuse는 모델과 프롬프트 버전, LLM 호출 단계, 토큰 사용량, 비용, 지연시간, 출력 검증 결과와 품질 평가를 담당한다.
- API 요청부터 AI 생성 완료까지 같은 `trace_id`를 전파하여 두 시스템의 데이터를 연결한다.
- `aigeneration` 모듈은 모델 호출과 출력 검증에 필요한 LLM span과 속성을 생성한다. 공급자 SDK와 Langfuse 전용 타입은 outbound adapter 밖으로 노출하지 않는다.
- PostgreSQL에는 재시도, 복구, 중복 방지와 사용자에게 보여 줄 상태처럼 제품 동작에 필요한 AI 실행 이력만 저장한다. 상세 telemetry를 운영 데이터베이스에 복제하지 않는다.
- 프롬프트, 응답, 개발 기록과 사용자 식별자는 기본적으로 관측 시스템에 원문 저장하지 않는다. 승인된 마스킹·보관·접근 정책이 적용된 필드만 수집한다.
- 상세 신호, 환경별 정책과 완료 기준은 [관측성 설계](./observability.ko.md)를 따른다.

## 변경 시 확인 사항

- 새 업무 기능은 어느 모듈이 소유하는가?
- 다른 모듈에 노출해야 하는 최소 공개 기능은 무엇인가?
- 핵심 규칙을 Spring이나 JPA 없이 테스트할 수 있는가?
- 스키마 변경에 순방향 Flyway 마이그레이션이 있는가?
- 실패와 재시도, 중복 실행 시에도 데이터 불변조건이 유지되는가?
- 새 실행 경로의 실패, 지연과 비용을 민감정보 없이 추적할 수 있는가?
