# 목표

개발 기록 저장 과정에서 AI 태그를 자동 생성한다. 기록 저장은 태그 처리 실패와 무관하게 유지한다.

완료 조건(현재 합의된 동작):
- 기록 저장 API는 기록 커밋 후 AI 호출·검증·태그 저장까지 기다린 뒤 응답한다.
- 화면은 전체 과정에 `저장 중…`을 표시한다.
- 기록 저장 실패는 오류로 반환하며 AI를 호출하지 않는다.
- 기록 저장 성공 후 태그 처리 실패는 기록 ID와 태그 처리 실패 여부로 구분한다.
- 태그 재생성 버튼은 기존 태그 유무와 관계없이 표시한다.
- 집중 테스트와 `verifyAll`을 통과한다. 세부 API 계약은 아래 승인 대기 권장안을 검토하여 구현 전에 확정한다.

## 범위

- 포함: devrecord 저장 흐름 조율, aigeneration AI 호출·응답 검증, 태그 저장, 재생성, 최소 화면 결과 표시.
- 제외: 비동기 선응답, 처리 상태 별도 저장, 폴링, 단계별 로딩, 자동 복구.
- 우선순위: 사용자의 주목표는 모니터링 시스템이다. 부가 UI 기능으로 범위를 늘리지 않는다. 모니터링 자체의 구현 범위는 아직 합의하지 않았다.

## 설계 정리 (2026-11-20)

### 대화에서 합의한 동작

- AI 입력은 aigeneration 전용 DTO로 분리한다. 필드는 title, workContent, problemContent, solutionContent, learnedContent다. devrecord가 입력을 변환한다.
- AI 출력은 기존 `List<ValidatedTag>`를 사용한다. 같은 필드의 결과 DTO를 추가하지 않는다. 정규화·중복 제거 후 1~5개라는 검증 규칙을 유지한다.
- devrecord의 조율 서비스는 트랜잭션 없이 기록 저장, AI 호출·검증, 태그 저장을 순서대로 호출한다. 기록과 태그 저장은 각각 별도 빈의 트랜잭션에서 커밋한다.
- 저장 직후 현재 화면에서 결과를 표시한다. 생성 응답에는 저장된 기록, 저장된 태그, 태그 처리 성공 여부를 포함한다. 태그 실패 시 기록은 유지하고 빈 태그 목록과 실패 여부를 반환한다.
- 기록 저장 예외는 공통 예외 처리로 전달한다. 태그 처리 계층은 원인을 보존한 예외를 던지고 조율 서비스가 처리 가능한 실패만 잡아 실패를 기록한 뒤 부분 성공으로 변환한다. 일반 `Exception` 전체를 잡아 프로그래밍 오류를 숨기지 않는다.
- 재생성은 기존 태그 유무와 관계없이 가능하다. 성공하면 해당 기록의 태그 연결만 한 트랜잭션에서 교체하고, 실패하면 기존 연결을 보존한다. 공유 태그 자체를 삭제하지 않는다.
- 재생성 성공 응답은 새 태그를 포함한다. 실패 응답에는 실패 여부만 포함하고 화면은 기존 태그를 유지한다.
- 같은 기록의 중복 재생성은 409로 거절한다. 단일 서버 프로세스를 기준으로 기록 ID별 메모리 실행 가드를 사용하고, 획득한 요청만 finally에서 해제한다. 동시성 상세 학습은 보류한다.
- Gemini를 사용하며 기본 모델은 `gemini-4-hydrogen`으로 합의했다. 기능별 설정 재정의는 가능하게 하되 처음에는 같은 모델을 사용한다. 모델 가용성과 무료 한도는 실제 연동 전에 다시 확인한다.
- AI 호출 제한은 15초, 자동 재시도는 없다. 시간 초과는 태그 처리 실패다. SDK의 기본 재시도도 비활성화한다.
- 실패 기록에는 기록 ID, 오류 코드, 요청 식별자와 정제한 원인을 사용한다. 기록 본문, 프롬프트, AI 응답 원문, API 키는 기록하지 않는다. 영속 AI 요청 이력 및 관측 시스템 연동 범위는 별도 확인이 필요하다.

### 남은 세부 설계 권장안 (승인 대기)

- 공개 경계: aigeneration의 `application/port/in`에 태그 생성 계약을 정의하고 전용 입력 DTO, 기존 ValidatedTag·TagCategory 및 외부에서 처리할 AI 예외에 필요한 패키지만 `@NamedInterface`로 노출한다. 내부 서비스·출력 포트·SDK 타입은 비공개로 유지한다. 호출 의존은 devrecord → aigeneration이며 반대 방향 조회는 만들지 않는다.
- Gemini SDK는 aigeneration의 출력 어댑터에 격리한다. 버전 고정 및 의존성 검토는 구현 전에 수행한다. API 키·기본 모델·기능별 모델·호출 제한은 서버 설정으로 주입한다.
- 생성 API는 기존 `POST /api/dev-records`의 201과 Location을 유지한다. `ApiResponse`의 data를 `{record, tags, taggingSucceeded}`로 확장한다. record는 기존 상세 응답 필드를 따르고, tags 항목은 `{tagId, name, category}`로 제안한다. 브라우저에 노출하는 ID는 모두 문자열이다.
- 재생성 API는 `POST /api/dev-records/{recordId}/tags/regenerate?userId=...`로 제안한다. 인증 도입 전 userId 전달 방식은 기존 조회 API를 따른다. 성공은 200의 `ApiResponse` data에 `{taggingSucceeded: true, tags: [...]}`, 처리 실패는 200의 data에 `{taggingSucceeded: false}`만 반환한다. 존재하지 않거나 타인 소유인 기록은 기존 계약대로 404, 중복 실행은 409의 `ErrorResponse`를 반환한다. 입력 오류는 400, 예상하지 못한 서버 오류는 500이다.
- 태그 저장 어댑터는 예상 가능한 영속성 실패를 원인이 보존된 devrecord 소유 예외로 변환한다. 트랜잭션 커밋 시점 실패도 별도 저장 빈의 호출 경계에서 분류한다. 예상하지 못한 오류는 공통 500 처리로 전파한다.
- 태그 재사용 키는 기존 검증기의 `normalizedName + category`다. DB에서도 같은 키를 유일하게 보장하는 새 Flyway 마이그레이션을 추가한다. 기존 데이터 중복 확인·정리, 빈 DB 및 V2에서 업그레이드 검증이 필요하다. V1은 수정하지 않으며 번호는 구현 시 최신 상태에서 정한다.
- 실행 가드는 Spring 싱글턴에서 공유한다. 신규 저장의 최초 태그 처리도 재생성과 같은 가드를 사용해, 저장된 기록이 조회된 직후 들어오는 재생성과 겹치지 않게 한다. 가드 획득 시점과 기록 커밋 직후의 경합은 집중 테스트 대상으로 둔다.
- 화면 재조회 후에도 결과가 유지되도록 기존 목록의 태그 이름 배열을 실제 값으로 채우고 상세 조회에 태그를 포함한다. 추가 UI 기능은 만들지 않는다.
