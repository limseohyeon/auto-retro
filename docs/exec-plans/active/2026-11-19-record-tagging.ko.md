# 목표

개발 기록 저장 과정에서 AI 태그를 자동 생성한다. 기록 저장은 태그 처리 실패와 무관하게 유지한다.

완료 조건(현재 합의된 동작):
- 기록 저장 API는 기록 커밋 후 AI 호출·검증·태그 저장까지 기다린 뒤 응답한다.
- 화면은 전체 과정에 `저장 중…`을 표시한다.
- 기록 저장 실패는 오류로 반환하며 AI를 호출하지 않는다.
- 기록 저장 성공 후 태그 처리 실패는 기록 ID와 태그 처리 실패 여부로 구분한다.
- 태그 재생성 버튼은 기존 태그 유무와 관계없이 표시한다.
- 집중 테스트와 `verifyAll`을 통과한다. 세부 API 계약은 설계 단계에서 확정한다.

## 범위

- 포함: devrecord 저장 흐름 조율, aigeneration AI 호출·응답 검증, 태그 저장, 재생성, 최소 화면 결과 표시.
- 제외: 비동기 선응답, 처리 상태 별도 저장, 폴링, 단계별 로딩, 자동 복구.
- 우선순위: 사용자의 주목표는 모니터링 시스템이다. 부가 UI 기능으로 범위를 늘리지 않는다. 모니터링 자체의 구현 범위는 아직 합의하지 않았다.

## 현재 상태와 근거

- [기록 저장 서비스](../../../src/main/java/com/devlog/auto_retro/devrecord/application/service/DevRecordCreateService.java): 현재 클래스에 `@Transactional`, 저장 포트 호출 후 ID 반환.
- [기록 상세 DTO](../../../src/main/java/com/devlog/auto_retro/devrecord/application/dto/DevRecordDetail.java): AI 입력 후보 다섯 필드 포함.
- [태그 응답 검증기](../../../src/main/java/com/devlog/auto_retro/aigeneration/application/service/TaggingV1ResponseValidator.java): 이미 구현되어 있음.
- [초기 스키마](../../../src/main/resources/db/migration/V1__create_initial_tables.sql): tags, record_tags 존재. 모듈 소유권은 기존 코드에 명시되지 않아 아래 설계로 정리 중.
- [아키텍처](../../architecture-definition.ko.md): 모듈 간 엔티티·저장소 직접 참조 금지.
- 구현 변경과 검증 실행은 아직 하지 않았다.

## 작업 순서

- [ ] 모듈 간 입력·출력 계약 설계: AI 전용 입력 DTO와 반환 태그 타입, 공개 경계 결정. 모듈 의존 방향 검토.
- [ ] API 결과 계약과 재생성 교체·실패·중복 요청 정책, AI 공급자·설정 확정. 사례로 설계 검토.
- [ ] 사용자 설계 승인 후 사용자가 구현. 직접 구현을 명시적으로 요청하면 승인된 범위만 에이전트가 구현.
- [ ] 기록/태그 저장 트랜잭션, AI 실패 시 기록 유지, API 계약을 집중 테스트로 검증.
- [ ] 최소 화면 흐름과 재생성 동작 구현·검토, 전체 검증.

## 결정 기록

- 2026-11-19: AI 입력은 title, workContent, problemContent, solutionContent, learnedContent. 사용자 ID와 날짜 등은 AI 입력에서 제외.
- 2026-11-19: 초기에는 커밋 후 비동기 호출·선응답을 검토했으나 사용자가 변경 승인. 최종 결정은 태그 처리까지 기다린 뒤 응답, 화면은 단일 로딩.
- 2026-11-19: devrecord의 트랜잭션 없는 조율 서비스가 별도 Spring 빈인 기록 저장 서비스와 태그 저장 서비스를 호출. 각 저장 서비스에 트랜잭션을 적용하여 기록 커밋 후 AI 호출, 이후 별도 태그 커밋.
- 2026-11-19: aigeneration은 AI 호출·검증 후 결과 또는 해석 가능한 예외를 반환. devrecord가 태그 및 기록 연결 저장을 담당하는 방향에 동의.
- 2026-11-19: 조율 서비스가 태그 처리 예외를 최종 처리. 기록 저장 호출은 그 예외 처리 범위 밖에 둔다. 기록 저장 실패를 태그 실패로 취급하지 않는다.
- 2026-11-19: 결과에 recordId와 태그 처리 성공 여부가 필요함에 동의. `taggingSucceeded`는 후보 필드명이며 API 상세 계약은 미확정. 성공은 AI 호출뿐 아니라 검증과 DB 저장까지 완료한 경우.
- 2026-11-19: 태그 유무와 무관하게 재생성 가능. 생성 성공 시 기존 연결 교체, 실패 시 기존 태그 유지는 제안된 방향으로 최종 정책 확인 필요.
- 2026-11-19: 사용자는 프록시를 거치는 별도 빈 호출과 같은 클래스 내부 호출의 차이를 이해했다. 이 설명을 처음부터 반복하지 않는다.

## 검증

구현 후 실행할 명령:

```powershell
.\gradlew.bat test
npm --prefix frontend run format:check
npm --prefix frontend run lint
npm --prefix frontend run build
.\gradlew.bat verifyAll
```

- 집중 테스트 대상 클래스·선택 실행 명령은 구현 범위 확정 후 기록한다.
- 기록 커밋 실패 시 AI 미호출, AI 호출·검증·태그 저장 각각 실패 시 기록 유지, 성공 응답 계약을 테스트한다.
- 재생성 성공·실패 시 기존 태그 처리와 겹친 요청 정책을 검증한다.
- 수동: 전체 로딩, 기록 저장 실패 안내, 부분 성공 안내, 항상 보이는 재생성 버튼과 재요청 동작 확인.
- 스키마 변경 필요 여부 미정. 변경한다면 새 Flyway 마이그레이션 및 빈 DB/업그레이드 검증 추가.
- 현재 검증 결과: 미실행. 이 문서는 설계 인계용이며 기능 완료를 의미하지 않는다.
