# 관측성 설계

## 목적

Auto Retro의 서버 상태와 Gemini 기반 AI 생성 품질을 운영 중에 진단할 수 있게 한다. 관측 데이터는 장애 대응, 비용 확인, 프롬프트와 모델 변경의 품질 회귀 탐지에 사용하며 제품 데이터의 영구 저장소로 사용하지 않는다.

이 문서에서 **서버 관측성**은 애플리케이션과 인프라의 안정성을, **LLM 관측성**은 제품이 실행한 모델 호출과 생성 결과의 품질을 의미한다. 저장소 개발에 사용하는 coding agent의 활동은 범위에 포함하지 않는다.

## 기본 구조

```text
HTTP 요청 또는 Batch 실행
→ 애플리케이션 유스케이스
→ aigeneration outbound adapter
→ Gemini API

Spring Boot / Spring AI / 사용자 정의 계측
→ OpenTelemetry Collector
   ├─ 로그·메트릭·전체 요청 Trace → Elastic
   └─ LLM 관련 Trace              → Langfuse
```

OpenTelemetry Collector를 공통 수집 경계로 사용한다. 애플리케이션이 Elastic과 Langfuse의 전송 방식에 각각 결합되지 않게 하고, 필터링·샘플링·목적지 라우팅을 배포 구성에서 관리한다.

## 역할과 데이터 경계

### Elastic

Elastic은 시스템 장애를 탐지하고 원인을 좁히는 운영 관측 저장소다.

- HTTP 요청 수, 오류율, 지연시간과 상태 코드
- JVM CPU, 메모리, GC, 스레드와 프로세스 상태
- 데이터베이스 연결 풀과 쿼리 지연
- Gemini를 포함한 외부 API의 성공, 실패, timeout과 지연시간
- 애플리케이션 로그와 예외
- 운영 임계값 기반 알림

Elastic에서 LLM 호출의 성공 여부와 지연시간은 볼 수 있지만 프롬프트 품질 분석과 생성 결과 평가는 수행하지 않는다.

### Langfuse

Langfuse는 LLM 실행을 분석하고 모델과 프롬프트 변경을 평가하는 저장소다.

- 생성 유형과 LLM 실행 단계
- 공급자, 모델, 프롬프트 이름과 버전
- 입력·출력·전체 토큰 사용량과 계산 가능한 비용
- 모델 호출 지연시간과 성공·실패 상태
- 구조화 출력 파싱 및 비즈니스 검증 결과
- RAG를 도입하는 경우 검색 단계와 검색 결과 메타데이터
- Tool Calling이나 Agent를 도입하는 경우 도구 선택과 실행 단계
- 사용자 피드백, 자동 평가와 고정 평가셋 점수

현재 단일 Gemini 호출도 하나의 LLM trace로 기록한다. 이후 여러 단계의 Agent가 도입되면 같은 trace 아래에 모델, 검색, 도구 호출을 자식 observation으로 추가한다.

### PostgreSQL

PostgreSQL은 제품 동작에 필요한 상태의 기준이다.

- 생성 요청 유형과 대상 식별자
- 처리 상태와 재시도에 필요한 시각
- 멱등성 또는 중복 방지에 필요한 식별자
- 사용자에게 보여 줄 생성 결과와 정제된 실패 코드

토큰별 세부 내역, span 트리, 원문 로그처럼 운영 분석만을 위한 데이터는 PostgreSQL에 중복 저장하지 않는다. AI 실행 이력 테이블의 구체적인 필드는 첫 AI 생성 유스케이스 설계에서 확정하고 Flyway 마이그레이션으로 추가한다.

## 상관관계와 공통 속성

HTTP 요청, Batch 실행, 애플리케이션 서비스와 Gemini 호출 사이에 OpenTelemetry context를 전파한다. Elastic과 Langfuse에서 같은 실행을 찾을 수 있도록 다음 식별자를 사용한다.

- `trace_id`: 한 요청 또는 한 Batch 작업의 전체 실행
- `generation_id`: 제품이 저장하는 AI 생성 실행 식별자
- `operation`: `TAGGING`, `SUMMARY`, `WEEKLY_REPORT`, `PRESENTATION` 같은 생성 유형
- `provider`: 모델 공급자. 초기값은 Google
- `model`: 실제 호출한 Gemini 모델 식별자
- `prompt_name`, `prompt_version`: 배포된 프롬프트 식별자
- `status`: 성공, 검증 실패, 공급자 실패, timeout 같은 정규화된 결과
- `input_tokens`, `output_tokens`: 공급자가 제공할 때만 기록
- `validation_result`: 구조화 응답 파싱과 도메인 검증 결과

사용자 ID나 개발 기록 ID는 원문 대신 추적 목적의 비가역 가명 식별자 또는 접근 통제된 내부 식별자를 사용한다. 이메일, 사용자 이름, 개발 기록 본문과 같은 고카디널리티 원문은 속성이나 로그 라벨로 사용하지 않는다.

## 민감정보와 보관 정책

- 프롬프트와 응답 원문 수집은 모든 환경에서 기본 비활성화한다.
- 원문이 필요한 진단 또는 평가 기능은 마스킹 규칙, 접근 권한, 보관기간과 삭제 절차를 먼저 승인한 후 별도로 활성화한다.
- API key, 인증 헤더, 데이터베이스 접속 정보와 환경변수는 어떤 관측 신호에도 포함하지 않는다.
- 예외는 공급자 응답 전문이 아니라 정규화된 오류 유형과 정제된 메시지를 기록한다.
- 메트릭 라벨에는 사용자 ID, 요청 ID, 프롬프트 원문처럼 값의 종류가 계속 늘어나는 필드를 넣지 않는다.
- 운영 환경의 sampling과 보관기간은 비용, 장애 조사 기간과 개인정보 요구사항을 근거로 정한다.

## 환경별 정책

| 환경 | Elastic | Langfuse | 원문 프롬프트·응답 |
|---|---|---|---|
| test | 외부 전송 없음 | 외부 전송 없음 | 수집하지 않음 |
| local | 선택적으로 로컬 전송 | 명시적으로 활성화할 때만 전송 | 기본 비활성화 |
| 운영 | 로그·메트릭·Trace 전송 | LLM Trace 전송 | 승인된 마스킹 정책이 있을 때만 제한적으로 수집 |

Exporter endpoint, 인증 정보, sampling 비율과 환경 표시는 환경변수 또는 배포 secret으로 주입한다. 저장소의 `application-*.yml`과 `.env` 예시에는 실제 비밀값을 넣지 않는다.

## 대시보드와 알림

### 서버 운영

- 전체 요청량, 4xx·5xx 비율과 p50·p95·p99 지연시간
- JVM heap, GC pause, CPU와 스레드
- 데이터베이스 연결 풀 고갈과 쿼리 지연
- Gemini 호출 오류율, timeout 비율과 지연시간
- 배포 버전별 오류 변화

운영 알림은 즉시 대응할 수 있는 증상과 임계값에만 설정한다. 초기 임계값은 부하 기준선을 수집한 후 확정한다.

### LLM 운영

- 생성 유형과 모델별 성공률 및 지연시간
- 입력·출력 토큰과 추정 비용 추이
- 구조화 출력 파싱·검증 실패율
- 프롬프트 버전별 품질 점수와 사용자 피드백
- 모델 또는 프롬프트 배포 전후 회귀 비교

품질 알림은 단일 응답의 주관적 판단이 아니라 승인된 평가셋과 점수 기준을 사용한다.

## 구현 책임

- 공통 OpenTelemetry와 exporter 구성은 애플리케이션 인프라 설정에서 관리한다.
- HTTP, JVM, 데이터베이스와 Spring Modulith 신호는 Spring Boot Actuator, Micrometer와 지원되는 계측을 우선 사용한다.
- `aigeneration` outbound adapter는 모델 호출 span과 LLM 전용 속성, 공급자 오류 변환을 담당한다.
- 애플리케이션과 도메인 계층은 Langfuse, Elastic 또는 공급자 SDK 타입에 의존하지 않는다.
- 관측 실패가 제품 요청을 실패시키지 않도록 exporter 전송은 애플리케이션 실행 경로와 분리한다.

## 완료 기준

- 한 AI 생성 요청의 `trace_id`로 Elastic의 서버 Trace와 Langfuse의 LLM Trace를 연결할 수 있다.
- Elastic에서 HTTP/JVM/DB/외부 API의 핵심 로그·메트릭·Trace를 확인할 수 있다.
- Langfuse에서 모델, 프롬프트 버전, 토큰, 지연시간, 상태와 검증 결과를 확인할 수 있다.
- test profile에서는 외부 관측 시스템에 네트워크 요청을 보내지 않는다.
- 기본 설정에서 프롬프트, 응답, 개발 기록과 비밀값이 전송되지 않음을 자동 테스트 또는 수집 결과 검사로 검증한다.
- exporter 또는 관측 백엔드 장애 중에도 제품 요청이 정의된 방식으로 처리된다.
- 집중 테스트와 `verifyAll`이 통과한다.

## 구현 전 결정 사항

- Elastic과 Langfuse를 Cloud로 사용할지 자가 호스팅할지
- 운영 환경의 sampling 비율과 데이터 보관기간
- 원문 프롬프트·응답 수집을 허용할 환경과 마스킹 기준
- 비용 계산에 사용할 모델 가격 정보의 관리 위치
- 초기 대시보드와 알림 임계값을 확정할 운영 기준선 수집 기간
